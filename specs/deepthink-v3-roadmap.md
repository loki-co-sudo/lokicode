作成: 1.11.1 時点。対象: 今後の複数バージョン。
位置づけ: [frontier-roadmap.md](frontier-roadmap.md)（P1〜P7）の**続き**。番号は P8 から継続する
（`reasoning.ts` のコメントが `frontier-roadmap P2` などを参照しているため、振り直さない）。

本書は2部構成。

- **第1部 設計レビュー**: 現行パイプラインを「何を足すか」ではなく「何が壊れているか・
  何を削るか」の観点で点検した結果。コードの実測（行番号つき）を根拠にする。
- **第2部 ロードマップ P8〜P13**: 優先順位つきの改善計画。各項目は
  動機（研究根拠）→ 実装スケッチ（触るファイル・ゲート）→ 検証 → コスト影響 を揃える。

## 0. 研究引用の扱い（重要な但し書き）

本書が参照する 2025〜2026 年の論文は、**タイトル・要旨レベルまでしか確認していない**
（2件のみ原典の要旨を取得: `arXiv:2604.16529` / `arXiv:2607.05391`）。
数値を実装判断の根拠に使う前に、必ず原典を確認すること。
出典に「二次情報」と注記したものは、ブログ等の伝聞であり一次資料を確認していない。

この但し書き自体が本リポジトリの方針（無根拠な数値の主張を JUDGE が CRITICAL 欠陥として
扱う）と一致する。ロードマップも同じ基準で書く。

# 第1部 設計レビュー

## 1.1 現行設計で正しいと確認できた点

- **オーケストレータ–ワーカ構造**（ブリーフ→調査→ドラフト→検証→合成）は、
  2026 年の deep research エージェント研究の主流と同型。特に「サブエージェントの
  文脈を分離し、凝縮した構造化出力だけを返す」形（`INVESTIGATOR` の
  VERIFIED / ASSUMPTIONS / UNKNOWN）は現在も推奨される設計。
- **適応的計算**（judge スコアによる早期終了、エフォートプリセット）と
  **検証の分離**（自己申告 `CONVERGED` の廃止）は、検証中心設計の潮流と一致する。
- **打ち切り時のまとめターン強制**（`agent.ts` `finalizeOnCap`）は、
  「長期タスクでは初期のツール誤りが下流に累積する」という指摘への正しい対処。

つまり**骨格は変えなくてよい**。以下の欠陥はすべて骨格の中の運用の問題である。

## 1.2 欠陥 A: 未計測のレバーの上に積み増している（最優先）

`frontier-roadmap.md` は P2 / P4 / P5 / P6 / P7 について「未計測」「効果未確認」を
自ら4箇所で明記している。効果が測れていない5つのレバーの上に6つ目を足すのが、
現状もっとも大きなリスク。

- CLAUDE.md「完了の定義」5 は、spec に検証節があるなら計測まで行うことを要求している。
  有料 e2e（`npm run e2e:deepthink`）が唯一の計測手段になっているため、
  実質「計測しない」が既定化している。
- **対策**: 第2部 P8（決定的評価ハーネス）を**他のすべてに先行して**実装する。
  P8 が入るまで、新しい生成系レバーを追加しない。

## 1.3 欠陥 B: コスト効率ルーティングの前提が現状と乖離している

[deep-reasoning-v2.md](deep-reasoning-v2.md) §11 は「高コストな強モデル呼び出しが実質 3→1」と
書いているが、これは**現在は成立していない**。`cost.ts` の `pipelineShape`（唯一の真実源）で
実際に数えると:

| 条件（オート判定 deep-hard 相当） | 強モデル呼び出し | 安価モデル呼び出し |
| --- | --- | --- |
| depth 5 / breadth 3 / balanced（N=2, J=1）・分解なし | **9**（brief 1 + judge 5 + final 3） | 13 |
| 同上・分解あり（P3 発火） | **10**（brief 1 + judge 5 + final 3 + compose 1） | 13 |
| depth 5 / breadth 3 / quality（N=3, J=2）・分解なし | **15**（brief 1 + judge 10 + final 4） | 14 |

内訳の根拠: `cost.ts:255` の `strongPlain = brief + finalPlain + judge + compose + beamJudge`。
`judge` は `depth × judgeSamples`（`cost.ts:187`）で、**深さに比例して強モデル呼び出しが増える**。
さらに `refine` は低スコア時に synthesis へ昇格する（`reasoning.ts:1047`）が、概算では
安価側に計上されているので、実際の強モデル比率は表よりさらに高い。

なぜ乖離したか（＝見直すべき変更が特定できる）: §11 執筆時（0.27.0）の構造は
brief 1 + final 1 の計2本だった。そこに **0.28.0 のアンサンブル**（final が `N+1` 本に）と
**0.42.0 の強モデル JUDGE**（judge が強モデル側へ移動）が乗った結果、
強モデル呼び出しが深さと幅の両方に比例するようになった。どちらの変更も個別には正当だが、
**§11 の「3→1」という記述だけが更新されずに残っている**。

つまり設計原則2（量は安価モデル・要所は強モデル）に対し、**judge が「量」の側に移動している**。
これは判定器を安価モデルへ下げる理由には**ならない**（CLAUDE.md の禁止事項）。
下げるべきは**モデルの格ではなくトークン量と冗長判定**である（P13）。

## 1.4 欠陥 C: 証拠予算が構造を壊す（文脈設計の劣化）

`joinEvidence`（`reasoning.ts:451`）は 9000 文字を調査件数で等分し、各件を**末尾切り捨て**する。
調査出力は VERIFIED → ASSUMPTIONS → UNKNOWN の順に並ぶため、切り捨ては
**UNKNOWN（＝何が未確認かの情報）から先に消える**。結果として下流のドラフト/判定は
「未確認である」という最重要のメタ情報を失った状態で読むことになる。

また breadth=5 では1件あたり約1700文字まで縮むため、`file:line` 引用つきの
VERIFIED 行が途中で切れる（引用の欠落＝接地の劣化）。

長期エージェント研究の一致した結論は「**素朴な切り詰めではなく構造を保った圧縮/退避**」であり、
ここは低コストで効く典型的な改善点（P11）。

## 1.5 欠陥 D: MoA の前提（誤りの非相関）が満たされていない

`reasoning.ts:937-941` のアンサンブルドラフトは、**完全に同一のメッセージ列**から
`ensembleSamples` 本を並列生成している（temperature 差のみ）。MoA / best-of-N が効くのは
提案者の誤りが相関しないときであり、同一文脈・同一モデル・同一指示では相関が高い。
結果として「N 倍のコストで N 倍未満（場合によってはほぼゼロ）の多様性」を買っている。

同じ問題が最終候補（`reasoning.ts:1068-1074`）にもある。

## 1.6 欠陥 E: 実行パスは設定次第で検証がゼロになる

`reasoning.ts:772-773`:

```ts
const verifyCmd = getVerifyCommand();
if (!aborted() && editedCount > 0 && verifyCmd) {
```

実行（fast path）では読み取り専用の解析ループ（調査・ドラフト・judge）を**すべてスキップ**する。
したがって検証コマンドが未設定なら、**そのランには LLM 判定も実行判定も一切存在しない**。
「ファイルを書き換えて終わり」になる。設計原則4（検証の分離）が設定依存で無効化される経路。

副次的に、`cost.ts` の `pipelineShape` は**解析パスしかモデル化していない**ため、
実行パスのランでは概算（invest / judge / final を含む）と実際（execute + verify）が構造的に
食い違う。これは表示の問題にとどまらない:

- **事前概算**（`ChatPane.tsx:596` の依存配列にはルート判定も `needsExec` も無い）は
  送信前に評価されるため、実行パスかどうかを知りようがない。解析パスを上限として
  出す現状は**安全側**なので、この点は仕様として明記すればよい。
- **事後校正は実害がある**: `structuralCalls` は「観測した実呼び出し数 ÷ 構造呼び出し数」で
  `toolMult` を学習する（`cost.ts:203-218`）。実行パスのランを解析パスの構造数で割ると、
  **一度も走っていない形状に対して係数を学習している**ことになり、`toolMult` が歪む。
  `needsExec` は実行時には確定しているので、校正側だけは実行パス形状で記録できる。

実行パスに構造呼び出しを足す変更をするなら、この校正側の不整合も同時に直す必要がある。

## 1.7 欠陥 F: 引用（file:line）を誰も検証していない

JUDGE は「証拠に現れないファイル名・関数名を欠陥とみなせ」と指示されているが、
judge が見るのは**証拠テキストだけ**で実ファイルではない。したがって
「実在しないファイルの実在しない行を、もっともらしく引用した VERIFIED 行」は
証拠テキスト内で自己完結しているため、**判定を素通りする**。

引用の実在確認は LLM を使わずに決定的にできる（ファイルを読んで行番号と文字列を照合するだけ）。
軸1（検証信号を LLM から実行に変える）の中で**最も安い**未回収の果実（P9）。

## 1.8 削る/強めるゲートの提案（足す前に）

- **削る候補**: なし（既存レバーはどれも計測前で、削る根拠がまだない）。
  ただし P8 の計測で効果が出なかったレバーは、次版で**削除を第一候補**とする。
- **ゲートを強める候補**: quality エフォートの `judgeSamples: 2` × 深さは強モデル呼び出しを
  倍にする（1.3 の表）。P13 の基準分解が入るまでは、深さ上限との組み合わせに注意する。

# 第2部 ロードマップ

実装順は依存関係で決まる: **P8 →（P9・P10 は並行可）→ P11 → P12 → P13**。
P8 なしに P11〜P13 を入れると、効果の有無が永久に判別できない。

## P8. 決定的評価ハーネス（非 LLM グレーダ）〔計測基盤・最優先〕

> **実装状況 (1.11.1)**: `src/lib/citations.ts`（引用抽出・段階1/2検証）・
> `src/lib/graders.ts`（citations/exit/edits/forbidden/calls の5グレーダ）・
> `src/lib/harnessReport.ts`（TSV 整形・回帰差分）・`e2e/harness/tasks.ts`
> （固定タスク6件）・`e2e/harness.e2e.ts`（ランナー）を実装済み。純ロジックは
> `npm test` でユニットテスト済み（`citations.test.ts` / `graders.test.ts` /
> `harnessReport.test.ts`）。**ただし**タスクセットは現状すべて「deep」ルート
> （読み取り専用）で、`edits` / `exit` / `forbidden` グレーダはハーネスの
> タスクではまだ使われていない（`e2e/tauriShim.ts` が `write_text_file` /
> `run_command` を許可しておらず、実行パスの安全なサンドボックスがまだ無い
> ため。この配線は P10（実行パス検証・サンドボックス実装が本来必要な項目）
> で行う）。**「既存 P2/P4/P5/P6 を遡って計測」は未実施**（`npm run
> e2e:harness` は有料の実 API 呼び出しを伴うため、CLAUDE.md「完了の定義」5
> に従いユーザーの実施可否確認を待っている）。

- **動機**: 現状の唯一の計測手段が有料の実走 e2e であり、実質計測されていない（欠陥 A）。
  推論時スケーリングの評価は再現性が主要な争点であり
  （*Test-Time Scaling in Reasoning LLMs: Inference Regimes, Evaluation, and Reproducibility*,
  arXiv:2608.04001 — 要旨のみ確認）、**判定を LLM に頼らないグレーダ**を持つことが前提になる。
  本リポジトリの CLAUDE.md「完了の定義」5 が要求する計測を、安価に常時可能にするのが目的。
- **実装スケッチ**:
  1. `e2e/` に固定タスクセット（5〜8件）を置く。各タスクは
     `{ prompt, route想定, graders[] }` の JSON。
  2. グレーダは**すべて非 LLM**:
     - `citations`: 最終回答中の `path:line` がすべて実在し、行番号がファイル行数以内か
       （P9 の `validateCitations` 段階1 を共用。抜粋の照合＝段階2 は、P9 で調査出力の
       形式を変えたあとに有効化する）。
     - `exit`: 期待するコマンド（`npm test` 等）の exit code。
     - `edits`: 期待するファイルが実際に変更されたか（変更前後のハッシュ差）。
     - `forbidden`: 触ってはいけないファイルが変更されていないか（CONSTRAINTS の機械化）。
     - `calls`: `[deepthink]` の LLM 呼び出し数・フェーズ別秒数（構造の回帰検出）。
  3. 出力は1行1タスクの TSV（合否・スコア・呼び出し数・秒数・実コスト）。
     前回結果との差分を表示する（回帰検出）。
  4. **モデル固定・シード固定**の「安価モード」を用意し、CI ではなくローカルで回す想定にする。
- **ゲート**: なし（開発者向けツール。ユーザー体験に影響しない）。
- **検証**: ハーネス自身のユニットテスト（各グレーダの純ロジック）。
  既存 P2 / P4 / P5 / P6 を**遡って**1回ずつ計測し、結果を frontier-roadmap.md の
  該当項目に追記する（「未計測」の解消がこの項目の完了条件）。
- **コスト影響**: `pipelineShape` 変更なし（アプリの呼び出し構造を変えない）。
  実走コストは残るが、非 LLM グレーダなので**判定側のコストはゼロ**。

## P9. 決定的な引用検証（citation validation）〔軸1・最安〕

> **実装状況 (1.11.1)**: 実装済み。`INVESTIGATOR`（`reasoning.ts`）の VERIFIED 行を
> `path:line — "抜粋" → 事実` 形式に変更し、`investigate()` の直後に
> `citations.ts` の `extractCitations` / `validateCitations` /
> `downgradeUnverifiedCitations` で機械検証・自動降格するゲートを追加した。
> `evidenceCache` への記録は `investigate()` の戻り値（降格後のテキスト）を
> 経由するため、5. の「記録前の検証」も自動的に満たされる（別配線は不要）。
> ユニットテストは `citations.test.ts`（抽出・段階1/2・降格の発火/非発火を
> 件数で assert）。**P8 グレーダでの導入前後比較は未計測**（有料実走待ち）。

- **動機**: 欠陥 F。引用の実在確認は LLM 不要で決定的にでき、判定側の知能に依存しない
  地上真実になる。検証を独立した軸として増強すると精度が上がることは
  *LLM-as-a-Verifier*（arXiv:2607.05391、要旨確認済み）の「criteria decomposition /
  repeated evaluation で検証精度が上がる」という主張とも整合する。
- **実装スケッチ**:
  1. **先に出力形式を変える（この項目に含める）**: 現行の `INVESTIGATOR`（`reasoning.ts:206`）は
     「file:line 引用つきの箇条書き」しか要求しておらず、書かれるのは行の**説明**であって
     行の**引用**ではない。したがって「引用文字列が該当行に含まれるか」の照合は
     **そのままでは実施できない**。VERIFIED 行の形式を
     `- path:line — "実際の行の抜粋" → 事実の記述` に変更し、抜粋を必須にする。
  2. `lib/citations.ts`（新規・純ロジック＋読み取り関数注入）:
     `extractCitations(text) → {path, line, quote?}[]` と
     `validateCitations(cites, readFile) → {ok, invalid[]}`。
     検証は2段階で、**段階1は形式変更前でも動く**:
     - 段階1（必須）: パスが実在し、行番号がファイルの行数以内であること。
     - 段階2（1 の形式変更後）: 抜粋が該当行（前後1行の許容）に含まれること。
       抜粋が無い引用は段階1のみで判定し、**不一致扱いにはしない**（誤検出の回避）。
     パス解決は `reasoning.ts` の `makeCitedFileReader` を再利用する。
  3. **調査出力のゲート**: `investigate()` の直後に検証をかけ、実在しない引用を持つ
     VERIFIED 行は **ASSUMPTIONS へ降格**（削除ではなく降格＝情報を捨てない）。
     降格件数を `[deepthink] citations` としてログに出す。
  4. **判定への合流**: 検証結果を JUDGE へ「機械検証済みの欠陥」として渡す。
     **重要な非対称性**: 決定的検証は**欠陥を追加する方向にのみ**効く。
     合格（`score >= passScore`）を与える権限は引き続き強モデル JUDGE だけが持つ
     （CLAUDE.md「判定器を安価モデルに下げない」に抵触させないための設計上の要）。
  5. `evidenceCache` の記録前にも同じ検証を通す（偽の事実を蓄積させない）。
- **ゲート**: `useTools && workspaceRoot` があるときのみ（読めるファイルが前提）。
- **検証**: `citations.test.ts` — 抽出（絶対/相対パス・行範囲・全角コロン）、
  実在しないパス・行番号超過の棄却、抜粋つき引用の不一致棄却、
  **抜粋なし引用が不一致扱いにならないこと**、**降格が実際に発火したこと**を
  件数で assert（CLAUDE.md「発動したこと自体を assert」）。
  P8 の `citations` グレーダで、導入前後の無効引用率を比較する。
- **コスト影響**: **LLM 呼び出しはゼロ**（`pipelineShape` 変更なし）。
  ファイル読み取りは投機的に増えるが、引用件数ぶんの `read_text_file` のみ。

## P10. 実行パスの検証を既定で有効化する〔軸1・品質デルタ最大〕

> **実装状況 (1.11.1)**: 実装済み。`src/lib/verifyCommand.ts`（`inferVerifyCommand`
> 純ロジック＋`detectVerifyCommand` 非同期ラッパー、優先順位はテスト済み）・
> `reasoning.ts` の実行パスに「検証コマンド未設定→推測→ユーザー承認1回→
> `lokicode.verifyCommand` に保存」の配線・`git diff` を強モデルに渡す
> grounded review（`GROUNDED_REVIEW`/`parseGroundedReview`、`editedCount > 0`
> のときのみ、検証コマンドの有無と無関係に発火する別ゲート）を追加した。
> `cost.ts` の `pipelineShape`/`structuralCalls` に `execPath`/`execReview`
> を追加し、**事前概算は execPath を渡さない（解析パス形状を安全側の上限と
> して維持）／事後校正（`ChatPane.tsx` の `recordToolRun` 呼び出し）だけが
> 実際のルートを渡す**という非対称性を実装（欠陥E後半の是正）。承認UIは
> 既存の承認ダイアログを再利用（`pending.name === "verify_command_suggestion"`）。
> ユニットテストは `verifyCommand.test.ts` と `cost.test.ts` の execPath 系。
> **未実施**: `e2e/harness/` のタスクセットへの配線（P8 のハーネスがまだ
> 書き込み/コマンド実行を許可するサンドボックスを持たないため — 別途の
> 安全なサンドボックス実装が必要で、本項目のスコープ外として据え置いた）。
> P8 グレーダでの exit/edits 導入前後比較も同じ理由で未計測。

- **動機**: 欠陥 E。検証コマンド未設定のランは無検証で終わる。実行結果（exit code）は
  判定側の知能に依存しない最強の信号なので、**設定忘れで失われるのが最大の損失**。
- **実装スケッチ**:
  1. `lib/verifyCommand.ts`（新規・純ロジック）: ワークスペース直下のファイルから
     検証コマンドを推定する。優先順位は
     `package.json` の `scripts.test` → `scripts.build` → `Cargo.toml` あり →
     `cargo test` → `pyproject.toml` あり → `pytest`。該当なしは空文字。
  2. `getVerifyCommand()` が空のとき、この推定値を**提案**として使う。
     初回は UI に「この検証コマンドで実行してよいか」を1度だけ確認し、
     回答を `lokicode.verifyCommand` に保存する（黙って任意コマンドを実行しない）。
  3. 実行後の grounded review（任意・別ゲート）: `git diff` を強モデルに渡し、
     ブリーフの CRITERIA / CONSTRAINTS 違反だけを指摘させる1回の判定を追加する。
     **これは構造呼び出しが増える**ので `pipelineShape` に `execPath: boolean` 引数と
     `execReview` フィールドを追加する（真のとき invest / suff / judge / refine / draft /
     final 系を 0、execute 系と `execReview` を数える）。
     ただし**2つの利用者を分けること**（欠陥 E 後半）:
     - **事前概算**（`estimateDeepReasoningCost`）は `execPath` を渡せない
       — 送信前にはルートも `needsExec` も未確定だから。解析パス形状を**上限**として
       出し続ける（安全側）。この前提を `cost.ts` のコメントに明記する。
     - **事後校正**（`structuralCalls` → `recordToolRun`）は `needsExec` 確定後に呼ばれるので、
       ここでは `execPath: true` を渡す。これで実行パスのランが解析パス形状で
       割られる現在の歪みが消える。
- **ゲート**: 推定コマンドの実行はユーザー承認が前提。grounded review は
  「ファイルを実際に編集した（`editedCount > 0`）」ときのみ。
- **検証**: `verifyCommand.test.ts`（各マニフェストからの推定・優先順位・該当なし）。
  `cost.test.ts` に `execPath` 分岐のテストを追加。
  P8 の `exit` / `edits` グレーダで、実行パスのランが検証まで到達する率を比較する。
- **コスト影響**: 検証コマンドは LLM 呼び出しではない。grounded review は
  強モデル +1 呼び出し（`execReview`）。ただし解析パス（9〜10 呼び出し）は走らないので、
  実行パス全体の呼び出し数は依然として解析パスより少ない。

## P11. 構造保存型の証拠圧縮（structured compaction / eviction）〔軸3〕

> **実装状況 (1.11.1)**: **前半（実装スケッチ 1〜3・joinEvidence の置換）は実装済み**。
> `src/lib/evidence.ts` の `parseFinding`/`compactEvidence` が VERIFIED（引用
> キーで重複除去）を最優先確保→UNKNOWN は件数のみでも必ず表示→ASSUMPTIONS/
> 自由記述は残り予算で丸ごと採用/退避、を実装。`reasoning.ts` の
> `joinEvidence` はこの実装に委譲するよう置き換えた（呼び出し側のシグネチャ
> は不変）。退避発生時は `[deepthink] evidence · ...` をログ出力。
> ユニットテストは `evidence.test.ts`（重複除去・退避の発火をカウントで
> assert・VERIFIED が引用途中で切れないこと・'none' プレースホルダの
> 除外・純粋性）。
>
> **後半（実装スケッチ 4）も実装済み**（別コミット）。`src/lib/agentCompaction.ts`
> の `shouldCompact`/`compactToolResults` を `agent.ts` の `runAgent` ループに
> 配線: 反復が `COMPACT_THRESHOLD`（15）を超えたランに限り、直近
> `KEEP_RECENT_TOOL_RESULTS`（5）件を除く古い `role:"tool"` メッセージの
> `content` を先頭 `COMPACT_KEEP_CHARS`（300）文字＋元の文字数の注記に
> **その場で書き換え**（削除・並べ替え・統合はしない）。絶対条件2点
> （`tool_call_id` の対応維持・`content` を空にしない）はユニットテストで
> 直接 assert（`agentCompaction.test.ts`）。冪等（2回目の圧縮は何もしない）
> もテスト済み。P8 グレーダでの導入前後比較は未計測。

- **動機**: 欠陥 C。素朴な末尾切り捨ては最重要情報（UNKNOWN・引用）から先に捨てる。
  長期エージェント研究では、切り詰めではなく**構造を保った圧縮・退避**が
  長時間動作の前提条件だと繰り返し指摘されている
  （*Beyond Compaction: Structured Context Eviction for Long-Horizon Agents*, arXiv:2606.11213;
  *Self-Compacting Language Model Agents*, arXiv:2606.23525;
  *CompactionRL*, arXiv:2607.05378 — いずれもタイトル/要旨レベルの確認）。
  文脈編集と記憶の併用で大幅な改善という報告もあるが、**二次情報のため数値は採用しない**。
- **実装スケッチ**:
  1. `lib/evidence.ts`（新規・純ロジック）: 調査出力を
     `{verified: Line[], assumptions: string[], unknown: string[]}` にパースする。
  2. `joinEvidence` を**構造保存型の予算配分**に置換:
     ① 全件の VERIFIED（引用つき）を最優先で確保 → ② UNKNOWN の見出しは
     件数のみでも必ず残す → ③ 余った予算を ASSUMPTIONS と本文散文に配る。
     重複した VERIFIED 行（同一 `path:line`）は**先に重複除去**してから予算を計算する。
  3. 予算超過時は「切り捨て」ではなく「**退避**」: 落とした件数を
     `（VERIFIED 12件中 4件を予算のため省略）` の形で明示し、下流が欠落を認識できるようにする。
  4. 実行フェーズ（`runAgent`、上限 50 反復）にも同型の圧縮を入れる。
     反復ごとに全会話を再送している現状（`agent.ts:496` の `conv`）は、長いランで
     遅延・コストが二乗的に悪化する。まずは**ツール結果のみ**を対象に、
     古い結果を「要約＋参照」に置換する（コード編集の履歴は落とさない）。
     **絶対条件（2つ）**:
     ① `{role:"tool", tool_call_id}` は直前の assistant の `tool_calls` と1対1で対応する。
     圧縮は**該当メッセージの `content` をその場で書き換える**方式に限り、
     メッセージの削除・並べ替え・統合をしてはいけない（対応が壊れれば API が拒否する）。
     ② 書き換え後の `content` を**空文字にしない**。
     [fix-roadmap-deepthink-400-crossplatform-shell.md](fix-roadmap-deepthink-400-crossplatform-shell.md)
     修正1 が記録するとおり、空 content・会話途中の system・連続同ロールといった
     メッセージ列の構造崩れは、このアプリで実際に HTTP 400 を起こしている。
     圧縮はメッセージ列を触る処理なので、同じ罠を踏みやすい。
- **ゲート**: なし（既存の予算処理の置換）。ただし実行フェーズの圧縮は
  「反復が閾値（例: 15）を超えたときだけ」発火させる（短いランのコストを増やさない）。
- **検証**: `evidence.test.ts` — パース、重複除去、予算配分、**退避が発火したこと**を
  落とした件数で assert、正規化後もキーが distinct であることを precondition として assert
  （CLAUDE.md の空振りテスト禁止）。
  P8 の `citations` グレーダで、圧縮後の証拠に残る有効引用数の増加を確認する。
- **コスト影響**: `pipelineShape` 変更なし（呼び出し数は不変）。入力トークンは減る方向。

## P12. 提案者の脱相関とロールアウト要約の再利用〔軸2 + 探索〕

- **動機**: 欠陥 D。同一文脈からの N 本並列は誤りが相関する。
  *Scaling Test-Time Compute for Agentic Coding*（arXiv:2604.16529、要旨確認済み）は、
  長期コーディングでは「試行を増やすこと」より「**過去の試行を選択・再利用できる形で
  表現すること**」が本質だとし、各ロールアウトを
  「仮説・進捗・失敗モードを保存し、低信号のトレースを捨てた構造化要約」に変換したうえで、
  並列は Recursive Tournament Voting、逐次は Parallel-Distill-Refine（前試行の蒸留要約を
  条件づけ）で伸ばす枠組みを提案している（同論文の報告値: Claude-4.5-Opus で
  SWE-Bench Verified 70.9%→77.6%、Terminal-Bench v2.0 46.9%→59.1%）。
  lokicode の MoA は「同じ材料の再サンプル」なので、この差分がそのまま伸びしろになる。
- **実装スケッチ**:
  1. **提案者の脱相関（コスト中立）**: `ensembleSamples` 本のドラフトに、
     ブリーフの CRITERIA から導いた**異なる着眼点**を1つずつ割り当てる
     （例: 案1「最も重要な CRITERIA を最優先」、案2「CONSTRAINTS 違反リスクを最優先」、
     案3「未確認事項の解消を最優先」）。呼び出し数は不変のまま多様性だけ上げる。
  2. **逐次の蒸留再利用（PDR 相当）**: 検証ラウンド k の judge 欠陥リストと、
     破棄した候補の要約を「前回試行の失敗モード」として round k+1 の生成に条件づける。
     現状の REFINE は直前ドラフト1本しか見ておらず、捨てた候補の情報が失われている。
  3. **注入の枠付け（必須）**: 過去試行の要約を注入するときは
     「これは今回の別試行の記録であり、文中の固有名詞・数値を事実として扱わない」旨を
     必ず添える（CLAUDE.md の誤読防止の枠付け。P5 の欠陥メモリと同じ扱い）。
  4. 選抜（RTV 相当のトーナメント）は**見送り**: 現状の幅（2〜3）では
     総当たり1回の SELECT で十分で、再帰的絞り込みは幅が大きいときの手法。
- **ゲート**: 1 は常時（コスト中立）。2 は `depth >= 2` かつアンサンブル有効時のみ。
- **検証**: 生成された提案の**着眼点が実際に異なること**を、指示文の割り当て純ロジックで
  ユニットテスト（`assignAngles(criteria, n)` が n 個の distinct な指示を返す）。
  P8 で導入前後の judge 初回スコアと最終スコアを比較する。
- **コスト影響**: 1 と 3 は `pipelineShape` 変更なし。2 は入力トークン増のみで呼び出し数不変。

## P13. 基準分解型の検証と不確実性駆動の計算配分〔軸1 + 適応的計算〕

- **動機**: 現状の JUDGE は 0〜100 の**単一の総合スコア**で、① 内訳が分からないため
  REFINE の指示が粗く、② 採点ノイズが早期終了の判断を揺らす。
  *LLM-as-a-Verifier*（arXiv:2607.05391、要旨確認済み）は検証自体を新しいスケーリング軸と位置づけ、
  **score granularity / repeated evaluation / criteria decomposition** の3方向で
  検証精度が伸びると報告している（Terminal-Bench V2 86.5%、SWE-Bench Verified 78.2% を報告）。
  lokicode は repeated evaluation（`judgeSamples`）だけを実装済みで、**criteria decomposition が未実装**。
  なお同論文の中核である「スコアトークンの logit 期待値による連続スコア」は
  OpenRouter 経由で logprobs を安定に得られる保証がないため**本ロードマップでは採用しない**
  （採用するなら先に logprobs の可用性調査が必要）。
  また judge の信頼性そのものに関する監査研究も、単一スコアの脆さを指摘している
  （*When the Judge Changes, So Does the Measurement*, arXiv:2607.08535 — 要旨レベル）。
- **実装スケッチ**:
  1. JUDGE の出力形式を、ブリーフの CRITERIA に**1対1で対応する内訳**に変更:
     `{"scores": {"c1": 0-10, ...}, "score": <加重合計>, "defects": [{"criterion": "c1", "issue": "..."}]}`。
     判定は**引き続き強モデル**（格を下げない）。パーサは既存 `parseJudgment` を拡張し、
     旧形式（単一 score）も受理する後方互換を残す。
  2. REFINE には「最も低い基準」だけを渡す（指示の焦点化。入力トークンも減る）。
  3. **不確実性駆動の停止/配分**: `judgeSamples >= 2` のとき、現状は min を取って
     分散を捨てている。基準ごとのばらつきを不確実性として使い、
     ・全基準で合格かつ低分散 → 即終了（今より早く止まる）
     ・合格だが特定基準の分散が大きい → その基準だけ再判定（部分的な repeated evaluation）
     とする。深さを一律に消費しない＝適応的計算の原則1に沿う。
  4. 強モデルの入力トークン削減（欠陥 B への対処）: judge にはドラフト全文＋全証拠ではなく、
     **主張リスト（claims）と対応する証拠行**を渡す形を検討する。これは判定器の格を
     下げるのではなく読ませる量を減らす施策であり、禁止事項に抵触しない。
- **ゲート**: 1・2 は常時。3 は `judgeSamples >= 2`（現状 quality のみ）。
- **検証**: `reasoning.test.ts` に拡張パーサのテスト（新形式・旧形式・壊れた JSON）、
  再判定の発火条件テスト（**発火したこと**を件数で assert）。
  `cost.test.ts`: 部分再判定を入れるなら `pipelineShape` の `judge` を
  `depth × judgeSamples + partialRejudge` に更新する（呼び出し数を変える変更なので必須）。
  P8 で、導入前後の「judge スコアと決定的グレーダ（citations / exit）の一致率」を比較する
  — これが判定器の質そのものの計測になる。
- **コスト影響**: 1・2 は呼び出し数不変・入力トークン減。3 は早期終了で減る方向と
  部分再判定で増える方向の両方があるため、P8 で実測して調整する。

## 見送り・次版候補（理由つき）

- **判定器の安価スクリーニング**（安価モデルで先に落とす）: CLAUDE.md の禁止事項に抵触。
  決定的検証（P9）は「欠陥を追加するだけで合格を与えない」という非対称性があるため可、
  という区別を守る。
- **回答キャッシュ**: 従来どおり禁止（P4 の原子的事実＋ハッシュ失効のみ）。
  ファイル単位のキー（質問横断で再利用）への拡張は魅力的だが、
  **原子的事実・ハッシュ失効・過去テキストの誤読防止の枠付け**の3条件を満たす設計を
  spec に書いてから着手する。
- **RTV（再帰トーナメント選抜）**: 幅 2〜3 では利得が小さい。幅を上げる方針を取るなら再検討。
- **logit ベースの連続スコア**: OpenRouter の logprobs 可用性調査が先。
- **P7 バンディットの選択有効化**: 引き続きデータ待ち。ただし P8 のハーネスは
  台帳を安価に埋める手段にもなるので、P8 実装後に再評価する。

## 実装順の根拠

P8（計測がないと以降の効果が判別できない）→ P9 / P10（非 LLM または設定の欠落を埋める
最安・最大デルタ。互いに独立）→ P11（全フェーズの入力品質の土台）→ P12（P11 の構造化要約を
前提に再利用する）→ P13（判定器の作り直しは影響が広いので、計測基盤と証拠構造が整ってから）。

## してはいけないこと（本ロードマップの文脈）

- P8 を飛ばして P11〜P13 を実装しないこと（未計測の上に未計測を積む）。
- 決定的検証（P9）に合格判定の権限を与えないこと（強モデル JUDGE が唯一の合格判定者）。
- 実行パスに構造呼び出しを足すとき、`pipelineShape` の実行パス対応（P10）を後回しにしないこと。
- 過去試行の要約（P12）を、誤読防止の枠付けなしに注入しないこと。
